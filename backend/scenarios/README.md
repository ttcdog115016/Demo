# 實務應用情境測試說明

本資料夾為三種實務應用情境（醫療研究、金融分析、交通流分析）之測試腳本與設定檔。
每個情境以一份測試資料集，依序執行資料前處理、K-匿名化、差分隱私、再識別攻擊模擬與 CAP 前後對比，
另有一組權限控管與資料存取檢查。

測試資料集為模擬資料，不含任何真實個人資料，隨完整交付套件之 `03_測試腳本/實務應用情境/data/` 提供，
使用時複製至本資料夾之 `data/`。執行結果寫入 `out/`，不隨版控保存。

## 前置準備

環境建置方式與 `docs/manual_test/README.md` 相同（`uv sync` 或 `pip install -r requirements.txt`）。
以 uv 執行者，下列 `python ...` 指令前加 `uv run`。

K-匿名化之假名化鹽值由 `.env` 之 `OPEN_PETS_DEFAULT_SALT` 提供；未設定時不加鹽，照常執行。

## 一、測試資料集

`scenarios/data/` 置三份 CSV：`醫療研究.csv`（14 欄）、`金融分析.csv`（15 欄）、
`交通流分析.csv`（14 欄），每份 500 萬筆，涵蓋數值、字串、類別與時間四種資料型態。

## 二、設定檔

`scenarios/configs/` 置 18 份設定檔，即每個情境六份，對應六個處理端點各自須開啟之區塊：

| 檔名 | 用途 |
|---|---|
| `<情境>_preprocess.json` | 資料前處理 |
| `<情境>_k.json` | K-匿名化 |
| `<情境>_dp.json` | 差分隱私 |
| `<情境>_risk_k.json` | 再識別三攻擊（以 K-匿名產生去識別資料） |
| `<情境>_risk_dp.json` | 再識別三攻擊（以差分隱私產生去識別資料） |
| `<情境>_cap.json` | CAP 前後對比 |

各情境之處理對象：

| 階段 | 處理對象 |
|---|---|
| 資料前處理 | 姓名、車牌與證號雜湊、居住里與起點路口截至區或縣市、時間截至日、數值夾限、空值填補、代碼正規化 |
| K-匿名化 | 準識別欄位（出生日期／出發時間、性別、居住里／起點路口、車種）泛化後檢驗 k、l。居住里與起點路口已於前處理截至區或縣市，K-匿名化不再泛化 |
| 差分隱私 | 每個情境三個數值欄、一個時間欄與一個類別欄逐欄配置預算 |
| 再識別風險 | 以同一組準識別欄位與一個敏感欄位執行三攻擊，並對 K-匿名化與差分隱私前後資料各執行 CAP |

三個情境的時間類預算配給就診日期、交易時間、抵達時間。

## 三、執行情境測試

```bash
python scenarios/run_scenarios.py                     # 三情境各七步
python scenarios/run_scenarios.py --scenario 金融分析  # 只跑一種
python scenarios/run_scenarios.py --skip-risk         # 只跑前三步
```

處理後之資料集寫入 `scenarios/out/`，各步驟之耗時與輸出彙整為 `scenarios/out/執行結果.json`。

## 四、執行權限控管與資料存取檢查

```bash
python scenarios/check_access_control.py
```

檢查建立兩種角色之使用者、帳密正確登入、密碼錯誤與帳號不存在之拒絕、重複建立帳號之拒絕、
一般使用者呼叫帳號管理端點應被拒絕（403）、密碼未以明文留存，以及稽核軌跡之鏈式完整性，
結果寫入 `scenarios/out/權限控管檢查結果.json`。

本檢查會於 `data/users.db` 建立 `scenario_admin`、`scenario_user` 兩個測試帳號，
檢查完畢後應予刪除（`DELETE /api/v1/users/{username}`，或直接刪除 `users.db`）。

登入相關端點需簽章金鑰才啟用，本腳本會自行為受測伺服器帶入一組僅供檢查使用的金鑰，
故不必先於 `.env` 設定 `OPEN_PETS_JWT_SECRET`；若已設定則沿用該值。

## 執行時間參考

500 萬筆之執行時間見實務應用情境測試報告；權限控管檢查約 20 秒。

## 500 萬筆資料的資源需求與逾時

- **記憶體**：500 萬筆（單檔約 610~690 MB）載入、切分、自產 syn 並跑隨機森林，記憶體用量大。
  Docker Desktop（WSL2）預設只取主機 RAM 的一半（16 GB 主機僅約 8 GB），不足時會大量換頁，三攻擊可慢數倍甚至被 OOM 終止。
- **實測（2026-11-17／18）**：交通流分析情境、單一容器，`docker stats` 每 5 秒取樣（短暫尖峰可能漏掉，實際峰值只會更高）。
  Docker 虛擬機記憶體 12.5 GB、主機 15.6 GB、16 邏輯處理器。

  | 資料列數 | 版本 | 前處理（耗時／記憶體峰值） | 差分隱私三攻擊 `risk-dp`（耗時／記憶體峰值） |
  |---|---|---|---|
  | 100 萬 | 優化前¹ | 47 秒／1.35 GiB | 68 秒／2.08 GiB |
  | 200 萬 | 優化前² | 128 秒／3.67 GiB | 140 秒／4.48 GiB |
  | 200 萬 | 優化後 | 105 秒／1.65 GiB | 159 秒／2.95 GiB |
  | 500 萬 | 優化前¹ | 235 秒後 **OOM 被終止**（9 GiB 上限） | 未執行 |
  | 500 萬 | 優化後³ | 221 秒／6.46 GiB | 422 秒／6.66 GiB |
  | 500 萬 | 再加串流匯出⁴ | 132 秒／**2.88 GiB** | 426 秒／**3.70 GiB** |

  ¹ 映像檔 `open-pets-app:2.0.0`（pandas 3.0.3），記憶體上限 9 GiB。² 以優化前的程式（pandas 3.1.1）於同一環境重測，作為與「優化後」對照的基準。
  ³ 記憶體上限 11 GiB。
  ⁴ 「串流匯出」指 CSV 結果檔改為 16 MiB 緩衝直接寫檔（原本先在記憶體組出整份 CSV 字串、複製、再編碼成 bytes，三份同時存在；
  含中文的字串每字元 2 位元組，500 萬列時匯出階段就是記憶體峰值）。另含 K-匿名列抑制不整份複製、CLI 原地處理。
  以現行 main 的鎖定套件（pandas 3.1.1、pyarrow 26.0.1、numpy 2.5.5）建置的映像檔，掛入新程式碼執行；限制 4 核、記憶體上限 11 GiB，`docker stats` 每 2 秒取樣，
  與上列（16 核不限核、每 5 秒取樣）條件不同，**耗時不可直接比較**。**核心數也會影響記憶體**：隨機森林的執行緒數隨可用核心數增加，每個執行緒各配置暫存，
  所以 `risk-dp` 的 3.70 GiB 是 4 核下的值，16 核下先前量到 6.66 GiB。輸出檔與優化前逐位元組相同（前處理 MD5 `1e4c3eab…`，K-匿名 `a08c7804…`）。
  未用大緩衝時（預設緩衝）寫入 Docker Desktop 掛載的資料夾，匯出由約 20 秒拖到約 300 秒，故緩衝不可省。
  「優化後」指：加入 pyarrow（pandas 3 字串欄位改為緊湊儲存）、三攻擊只讀需要的欄位（identifier 欄位如雜湊後的車牌、證號不讀）、
  前處理不整份複製、推斷性攻擊分批評分（隨機森林對全部列整批預測時，每個執行緒都要配置「列數 × 類別數」的暫存陣列，500 萬列在 11 GiB 上限被 OOM）。
  200 萬列的記憶體峰值：前處理降約 55%、三攻擊降約 34%；三攻擊耗時多約 14%。500 萬列的優化前後對照只有前處理（優化前在 9 GiB 上限 OOM）。
  500 萬列三攻擊的報告與交付套件當初的結果一致（指認性 0.6304、連結性 0.0；推斷性 0.0006 對 0.0007，差分隱私含隨機雜訊）。

  500 萬列整套步驟的實測（各步驟單獨在記憶體上限 11 GiB 的容器執行，全部成功）：

  | 步驟（500 萬列） | 先前實測（16 核、每 5 秒取樣）耗時／峰值 | 現行 main⁴（限 4 核、每 2 秒取樣）耗時／峰值 | 結果 |
  |---|---|---|---|
  | `preprocess` | 221 秒／6.46 GiB | 132 秒／**2.88 GiB** | 輸出 MD5 與先前相同 |
  | `k-anonymity` | 396 秒／10.33 GiB | 167 秒／**3.78 GiB**（容器 cgroup 峰值 3.86 GiB） | k／l／t 皆通過，抑制率 0.0%，輸出與先前逐位元組相同 |
  | `dp` | 405 秒／6.32 GiB | 227 秒／**3.47 GiB** | 消耗 ε=3.5 |
  | `risk-k-anonymity` | 216 秒／6.24 GiB | 249 秒／3.15 GiB | 指認性 0.0、連結性 0.002、推斷性 0.0004 |
  | `risk-dp` | 422 秒／6.66 GiB | 426 秒／3.70 GiB | 指認性 0.6304、連結性 0.0、推斷性 0.0007 |
  | `risk-cap`（K-匿名結果） | 442 秒／5.40 GiB | 155 秒／**5.39 GiB** | CAP 0.9988 → 0.4507 |
  | `risk-cap`（差分隱私結果） | 210 秒／4.92 GiB | 163 秒／4.97 GiB | CAP 0.9988 → 0.9986 |

  上列各步驟的報告數字，與交付套件當初的 500 萬列結果一致（差分隱私含隨機雜訊，只比對報告數字）。
  串流匯出前，K-匿名處理是記憶體峰值最高的一步（10.33 GiB），峰值落在匯出結果檔的階段；改為串流匯出後降到 3.78 GiB，
  `preprocess`、`dp` 也同樣受惠（三者都經由匯出）。`risk-*` 不匯出資料，數字不因匯出而變。
  **16 執行緒、8 GiB 上限的整套實測**：隨機森林的執行緒數隨可用核心數增加、每個執行緒各配置暫存，`risk-*` 的記憶體因此隨核心數上升
  （上表限 4 核的 `risk-dp` 3.70 GiB，16 核先前為 6.66 GiB）。為量到 16 核主機的情況，這次讓 joblib 回報 16 核（`n_jobs=-1` → 16 個執行緒），
  實際 CPU 仍限 4 核、每步一個容器、記憶體上限 8 GiB；全部成功、沒有 OOM：

  | 步驟（500 萬列，16 執行緒、8 GiB 上限） | 耗時 | 容器峰值 | 結果 |
  |---|---|---|---|
  | `preprocess` | 149 秒 | 2.91 GiB | 輸出 MD5 與先前相同 |
  | `k-anonymity` | 161 秒 | 3.86 GiB | 輸出與先前逐位元組相同 |
  | `dp` | 239 秒 | 3.62 GiB | 消耗 ε=3.5 |
  | `risk-k-anonymity` | 330 秒 | **6.47 GiB** | 指認性 0.0、連結性 0.002、推斷性 0.0004 |
  | `risk-dp` | 432 秒 | **6.81 GiB**（最高） | 指認性 0.6304、連結性 0.0、推斷性 0.0006（差分隱私含隨機雜訊） |
  | `risk-cap`（K-匿名結果） | 146 秒 | 5.46 GiB | CAP 0.9988 → 0.4507 |
  | `risk-cap`（差分隱私結果） | 140 秒 | 5.05 GiB | CAP 0.9988 → 0.9986 |

  因此整套情境的 Docker 記憶體建議由「至少 12 GB」（原依 K-匿名舊峰值 10.33 GiB 訂定）調整為**至少 8 GB（已實測：8 GiB 上限下整套完成）**。
  **餘裕有限**：最高峰值 6.81 GiB 距 8 GiB 約 1.2 GiB（約 15%），同時還有其他負載、或資料欄位更多時可能不足，建議留到 10 GB 以上。
  （本環境 Docker 虛擬機 12.5 GB；未實測 8 GB 以下的上限。）

  **網頁介面（API）整體峰值**（500 萬列，每個端點用全新的隔離容器：限 4 核、記憶體上限 11 GiB、拋棄式資料與帳號，全部 HTTP 200、沒有 OOM）：

  | 端點 | 上傳大小 | 耗時（上傳＋處理＋下載） | 容器峰值 | 回應大小 |
  |---|---|---|---|---|
  | `/api/v1/preprocess`（原始 CSV） | 0.64 GiB | 95 秒 | 4.06 GiB | 1.06 GiB |
  | `/api/v1/k-anonymity`（前處理結果） | 1.06 GiB | 126 秒 | 5.79 GiB | 1.25 GiB |
  | `/api/v1/dp`（前處理結果） | 1.06 GiB | 177 秒 | 5.79 GiB | 1.04 GiB |

  API 的峰值比同一步驟的 CLI 高約 1~2 GiB（多了上傳內容的 bytes 與回應的 bytes），仍在 8 GiB 內。
  **預設上傳上限是 1024 MB（`OPEN_PETS_MAX_UPLOAD_MB`），前處理後的 500 萬列檔案為 1.06 GiB，超過預設上限**；上列實測把上限調到 2048 MB。
  以網頁介面處理這個規模的檔案前，須先調高該設定（見 `docker/README_Docker.md` 疑難排解的「上傳大檔失敗」，前端另有同樣的 1024 MB 限制）。
  網頁介面的 CSV 序列化已改為直接寫進 `BytesIO`，不再經「`StringIO` → `getvalue()` → `encode()`」三份複本：
  載入 500 萬列後單獨匯出，容器峰值 6.81 → 3.52 GiB、耗時 37.4 → 18.8 秒，輸出逐位元組相同（MD5 `1e4c3eab…`）。

  **差分隱私改為原地處理（省掉 `df.copy()`）的實驗沒有採用**：500 萬列下 CLI 的容器峰值 3.62 → 3.61 GiB、API 的 5.79 → 5.80 GiB，
  差距在量測誤差內，所以 DP 的峰值不在那份複製上；為避免「函式會改動呼叫端資料」的行為變更卻沒有好處，不納入。
  （K-匿名與前處理的原地處理先前已採用，單獨的效益也不大；記憶體的主要改善來自匯出方式。）
  本環境的耗時明顯長於交付套件當初的記錄（例如 CAP 當初約 55 秒、本次 442 秒；K-匿名當初約 158 秒、本次 396 秒），
  資料夾由 Windows 掛進 Docker（逐檔讀取慢）與機器規格不同都有影響，耗時請以各自環境為準。
  耗時方面，`risk-dp` 約每百萬列 70~80 秒，100 萬列起就超過 nginx 預設的 60 秒逾時（舊版 Demo 的 nginx 須設 `proxy_read_timeout`，見上）。
  以 `docker info --format "{{.MemTotal}}"` 查目前可用量；調高方式為建立 `%USERPROFILE%\.wslconfig`
  （`[wsl2]` 下 `memory=12GB`、`swap=16GB`），執行 `wsl --shutdown` 後重開 Docker Desktop。
- **命令列（CLI）無逾時上限**：本資料夾的 `run_scenarios.py` 與 `指令集` 逐步指令都不設逾時，500 萬筆建議以此執行，一次一個情境
  （`--scenario <情境>`）。
- **網頁介面（Step4）**：每個請求有前端逾時，預設至少 15 分鐘，並隨上傳資料量放大（每 MB 3 秒、上限 2 小時，500 萬筆約 32 分鐘）；
  K-匿名／DP 的三攻擊與 CAP 會依候選敏感欄位逐輪各送一次請求，各輪的逾時分開計算，但總等待時間會乘以輪數；
  大資料請在 Step2 只指定 1 個敏感欄位。三個情境的差分隱私設定各只有 1 個類別欄，通常是 1 輪。
  建置前端時可用環境變數 `VITE_API_TIMEOUT_MINUTES`（正數，分鐘）直接指定。逾時後後端通常仍在計算，請等它算完再重送。

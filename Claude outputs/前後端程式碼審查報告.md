**最嚴重的五項**，均已修正：

1. **登入鎖定可被並發繞過**：同時送 40 個錯誤密碼，計數只加 1。

## 一、後端：安全性與併發

### B1【高】並發錯誤密碼可繞過 5 次鎖定　✅ 已修

- **位置**：`app/governance/auth.py` 的 `authenticate`、`_record_login_failure`
- **問題**：
  - 驗證前讀出 `failed_login_count`，失敗時寫回「讀到的值 + 1」。
  - `/auth/login` 是同步端點，在約 40 條執行緒的池中並行，同時到達的錯誤密碼請求都讀到同一個值。
- **重現**：20 個執行緒同時以錯誤密碼登入。修正前帳號沒有被鎖，攻擊者實際可猜的次數約為設計值的 40 倍。
- **修正**：

```python
# 修正前：沿用驗證前讀到的計數
self._record_login_failure(username, fail_count, _from_text(first_failed_at))

# 修正後：在 BEGIN IMMEDIATE 交易內「重讀→加一→寫回」，同一時間只有一個請求能改
with sqlite3.connect(self.db_path, timeout=30) as conn:
    conn.execute("BEGIN IMMEDIATE")
    row = conn.execute("SELECT failed_login_count, login_first_failed_at FROM users WHERE username = ?", (username,)).fetchone()
    count, window_start, locked_until = self._next_failure_state(now, int(row[0] or 0), _from_text(row[1]))
    conn.execute("UPDATE users SET failed_login_count = ?, login_first_failed_at = ?, "
                 "login_locked_until = COALESCE(?, login_locked_until) WHERE username = ?", ...)
```

- **補強**：密碼驗證成功後，在同一交易內再確認一次未被鎖定，才清零。scrypt 驗證約需數十毫秒，期間其他請求可能已觸發鎖定。
- **測試**：`test_b1_concurrent_wrong_passwords_are_all_counted`、`test_b1_concurrent_burst_ends_locked`

### B2【高】同一 refresh token 並發可換發兩次；重複使用未被偵測　✅ 已修

- **位置**：`app/governance/token.py`、`app/api/auth_router.py` 的 `/auth/refresh`
- **問題**：
  - 原流程分三步：`resolve`（讀）→ `revoke`（無條件寫）→ `issue`。兩個請求同時拿同一張 token，兩個都成功、各拿到一張新 token。
  - 文件寫「舊 token 再次出現即代表外流」，但程式沒有做任何處置。
- **修正**：
  - 新增 `TokenManager.consume()`：在交易內只有真正把 token 從有效改為「已換發」（`revoked=2`）的那個請求成功。
  - 已換發的 token 再次出現時，撤銷該帳號全部 refresh token。
  - 登出、改密碼、停用帳號造成的作廢標為 `revoked=1`。這類 token 被舊分頁拿出來時只回 401，不連帶登出目前的登入（這是修正過程中由既有測試抓到的交互問題）。
- **測試**：
  - `test_b2_concurrent_refresh_only_one_succeeds`：8 個並發請求只有 1 個成功
  - `test_b2_reused_token_revokes_whole_session_family`
  - `test_b2_refresh_endpoint_rejects_second_use`

### B3【中】稽核雜湊鏈在並發寫入時斷鏈；每寫一筆就讀整個日誌　✅ 已修

- **位置**：`app/governance/audit.py` 的 `log_operation`、`_get_last_hash`
- **問題**：
  - 「讀上一筆雜湊 → 計算 → 追加」之間沒有互斥。兩筆同時寫入會指向同一個父雜湊，`verify` 會報為鏈結斷裂，看起來像被竄改。
  - `_get_last_hash` 每次都 `readlines()` 讀進整個 `audit.jsonl`。
- **修正**：
  - 加行程內 `threading.Lock` 包住整段。
  - 最後一行改由檔尾往前讀，區塊從 8 KB 起倍增，直到找到換行。
- **測試**：
  - `test_b3_concurrent_audit_writes_keep_chain_valid`：16 執行緒 × 10 筆
  - `test_b3_last_hash_read_from_tail_of_large_log`：單行 200 KB

### B12【中】取消運算的 handle 可被他人覆蓋；結束時誤刪別人的登記　✅ 已修

- **位置**：`app/api/compute.py`
- **問題**：
  - handle 由前端提供，原本直接覆寫 `_active_runs[handle]`。他人送出同一個 handle 就能搶走登記，原主按取消會被以 403 拒絕。
  - `finally` 一律 `pop(handle)`，可能刪掉後來同名運算的登記。
- **修正**：
  - `_register_run` 遇到他人已登記的 handle 不覆寫。該運算仍可經斷線偵測取消。
  - `_unregister_run` 只移除自己的 event。
  - 斷線偵測工作意外結束時寫入日誌。
- **測試**：`test_b12_handle_owned_by_other_user_is_not_overwritten`、`test_b12_finally_only_removes_own_registration`

## 三、後端：運算引擎

### E1【高】差分隱私先加噪才裁切，ε 保證不成立　✅ 已修

- **位置**：`app/engines/dp/pipeline.py`
- **問題**：`clipping_bounds` 只在加噪**後**處理超界。
- **重現**：
  - 設定：薪資 980 萬、sensitivity 5000、上界 20 萬。
  - 結果：加完 ±5000 的雜訊仍遠超上界，事後被夾到 20 萬，輸出「必定是 20 萬」。正常值落到 20 萬的機率約 e⁻³⁴，等於確定性地揭露「這筆是極端值」。
- **修正**：

```python
units = to_units(df_out[col], minimum_unit)
# 新增：加噪前先夾到上下界（換算成整數個最小單位）
if budget.clipping_bounds is not None:
    low, high = budget.clipping_bounds
    units = units.clip(lower=math.ceil(low / minimum_unit), upper=math.floor(high / minimum_unit))
```

- **測試**：`test_e1_values_clipped_to_bounds_before_noise`，直接攔截送進加噪器的值，必須 ≤ 上界。
- **仍需注意**：未設定上下界、只填 sensitivity 時，極端值仍無法被掩蓋。建議 Step3 對數值欄強制填上下界（見第五節）。

### E3【高】列抑制只做一輪，違反 k 的列仍被釋出　✅ 已修

- **位置**：`app/engines/anonymization/pipeline.py` 第 4 步
- **問題**：
  - 空值被當成萬用字元時，等價類大小不具單調性：完整列可能靠含空值的列湊滿 k，反之亦然。
  - 刪掉第一批違規列後，原本靠它們撐住的列會落到 k 以下，但程式不再重算。
- **重現**：
  - 資料：k=3，三列 (1, 空)、(1, 30)、(1, 40)。
  - 結果：第一輪只刪後兩列，留下的 (1, 空) 落單；報告 `k_passed=False`，資料仍輸出。
- **修正**：列抑制改為「重算 → 刪除違規列」迴圈，直到沒有違規列（最多 n 輪，每輪可取消）。
- **測試**：`test_e3_row_suppression_repeats_until_k_holds`

## 八、F12 大檔處理（2026-11-02 第三批）　✅ 已修

**目標**：本機 .exe（WebView2）處理數百 MB 的 CSV 時，不再把整份檔案讀成單一字串。V8 單一字串上限約 5.37 億字元，超過就會出現「Invalid string length」，而且整個流程原本會同時存在 4～6 份完整複本。

### 改了什麼
| 階段 | 原本 | 現在 |
|---|---|---|
| 共用工具 | — | 新增 `utils/blobStreaming.ts`（逐段解碼、去 BOM、轉碼、跨段列數計數、逐段 SHA-256）與 `utils/csvBlobParse.ts`（逐段解析 CSV，只在完整資料列處切段，引號規則與 Papa 相同，Worker 與測試環境皆可用） |
| Step1 上傳 | 整檔 `arrayBuffer` 後解碼成字串，再對字串做各項檢查 | 只讀前 64 KB 判斷編碼。UTF-8 直接沿用原檔；其他編碼逐段轉碼。標題列清理以「新標題＋原檔切片」組成新檔。亂碼、特殊字元、型別離群值三項檢查改為逐段處理；**超過 200 MB 只抽樣檢查前 200 MB，畫面會註明**。使用者選擇移除特殊字元時，逐段處理整個檔案 |
| Step4 原始資料 | `originalFile.text()`＋`.replace` 去 BOM | 只以 Blob 切片去 BOM |
| Step4 前處理結果 | `response.data.text()` | 同上，以 Blob 處理 |
| 輸入／輸出筆數 | 對兩份整檔字串計數 | 逐段計數（與原規則共用同一個狀態機，結果必定一致） |
| 風險評估上傳（欄位裁切＋分級距） | 整份解析成列陣列再轉回字串 | Blob 進、Blob 出，逐段轉換，每段立刻編成 UTF-8 位元組 |
| CAP 基線編碼 | 讀整份處理後文字 | 直接從 Blob 逐段編碼 |
| 實用性（保真度） | 把兩份整檔字串送進 Worker，各自完整解析 | 只把 Blob 傳進 Worker（傳參照，不複製）。**超過 200 MB 只取原始資料前 20 萬列**與配得到的處理後列計算，報告標示「抽樣計算」 |
| 檔案指紋 | 超過 512 MB 直接回 `null`（沒有指紋） | 512 MB 以下維持 Web Crypto；更大的檔案逐段累加計算 SHA-256 |

**仍會整份讀取**：Excel。SheetJS 必須讀入整份活頁簿，所以超過 100 MB 的 Excel 會跳出提示，建議先另存成 CSV（UTF-8）。

- 影響：超過 10 MB 的檔案，在欄位統計中每個段落邊界可能有一格被讀錯。這會用在 DP 上下界建議、風險評估等地方。
- 建議改用本次新增的 `parseCsvBlobInChunks`（已處理跨段字元）。

## 九、F9 DP 累計預算：維持暫緩，補充說明
- 「換一份新資料就重新累計」是正確的，累計本來就以**同一份資料集**為單位。
- 問題出在**同一份資料**：目前累計值只存在記憶體，重開程式、重新整理或重新上傳同一份檔案就歸零。同一份資料因此可以一再發佈，總消耗超過門檻也不會被發現。
- 另外，目前的門檻（預設 ε=20）只比對「本次」消耗，不是累計值。
- 若日後要處理：由後端依「資料集 SHA-256」記帳，換資料自然重新起算，同一份資料重開也不歸零。
